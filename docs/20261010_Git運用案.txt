Gitの運用案（コミットの単位）　ゆめかわ★ウイルス・ぽっぷ
========================================

※手順（SourceTreeの操作）は「Git使い方.txt」を参照。
※つなぎ目（関数の名前・データの形）は、仕様書の8章と10章。


＜基本の考え方＞

①1コミット ＝ 1つの意味のある変更
　「何をしたか」を一言で言えるところで区切る。
　（例：ノーツが落ちるようになった／判定が動いた）

②動く状態でコミットする
　コミットした時点で、ページを開いてエラーが出ないこと。
　途中のままコミットしない（壊れたまま残さない）。

③小さく、こまめに
　1回のコミットで、触るファイルは1〜2個くらい。
　大きくなりそうなら、先に分ける。

④担当外のファイルは触らない
　どうしても必要なときは、持ち主に声をかけてから。
　（ファイルの持ち主は、仕様書 2.2 の表）

⑤サンプル見本（sample/）は直さない
　読むだけ。直したいところは、本番のファイルで直す。


＜3つの見方＞

①他の人に見せたとき
　履歴を見て、誰が何を作ったか分かる。
　→ コミットメッセージに「何をしたか」を書く。
　→ 名前のついたブランチ（matsui-index など）で、担当が分かる。

②バージョン管理として
　あとから「動いていたところ」に戻れる。
　→ 動く状態でコミットする。
　→ 機能ごとにコミットを分けておくと、1つだけ取り消せる。

③画面とゲーム本体をつなぐとき
　画面（松井）とプレイ画面（中山）は、別々のファイルを触る。
　→ つなぎ目（関数の名前・データの形。仕様書の8章と10章）を
　　先に決めておけば、衝突しない。
　→ つなぎ目を変えたいときは、コミットする前に相談する。


＜コミットの例＞

★中山さん（プレイ画面）
　・ゲームの骨組みを追加（game.js）
　・譜面データを読み込めるようにした
　・ノーツが落ちるようにした
　・判定を追加（大優勝／神／超かわよ／ミス）
　・スコア・コンボ・HPを追加
　・メロディ音とBGMを追加（audio.js）
　・ウイルスの表示とHUDを追加（view.js）
　・曲データを追加（charts.js）
　・曲データの音を修正（耳で聴いて確認した）

★松井さん（画面・統合）
　・画面モックアップを追加（最初の1回だけ。全ファイルをまとめて main に入れる）
　・見本を追加（sample/。最初の1回だけ）
　・画面の切り替えを追加（screens.js）
　・セレクト画面の曲カードを、曲データから作るようにした
　・ランキング保存を追加（ranking.js）
　・本日のトップを表示した
　・リザルト画面を完成
　・中山さんのプレイ画面を統合

★岡野さん（テスト・仕上げ）
　・認定証の見た目を追加（result.css）
　・豆知識の文を追加（tips.js）【できれば】
　・テスト結果を記録（docs/test.md）


＜コミットメッセージのルール＞

　「何をしたか」を一言で書く。
　例）ノーツが落ちるようにした
　　　ジングルベルの譜面を修正
　　　セレクト画面に曲カードを追加

　× 修正　／　更新　／　あああ　　（何をしたか分からない）


＜プルリクエストのルール＞

①1つのプルリクエストには、1つのまとまった作業だけ入れる。
②タイトルに「何をしたか」を書く。
③リーダーが確認してからマージする（確認項目は「Git使い方.txt」）。
④マージしたら、作業ブランチは削除する。
⑤次の作業は、新しいブランチを作ってから始める。


＜AIが作ったコードをコミットするとき＞

※AIにコーディングを頼むときは、仕様書と、自分の担当のファイル（、必要ならサンプル見本の該当部分）を一緒に渡す。

①コミットする前に、必ず動かして確かめる。
②何をしているコードか、自分の言葉で説明できるようにしておく。
　（説明できない部分は、AIに聞いてから）
③AIにそのまま任せた部分があっても、コミットメッセージは自分で書く。
